# Part 8 — visual QA in development

The first capture module binds every screenshot, rendered HTML/layout artifact and finding to an immutable candidate revision and source digest. It checks the source before each route and between viewport batches, and rejects changed candidates rather than accepting mixed-revision evidence.

Desktop 1280×900 and mobile 390×844 cover every required route. Selected critical routes also run at 320×568, 844×390 landscape, 1440×320 short-height and 3440×1440 ultrawide. Each batch has its own isolated browser context and bounded network bridge. Capture callers provide an overall abort/deadline and artifact budget.

Deterministic findings currently cover HTTP failures, unobserved route states after redirects, horizontal overflow and visibly broken images. Each finding records the candidate, requirement, route, resolved route, viewport, reproduction steps and screenshot/HTML/structure IDs. A passing fixture and intentionally broken fixture verify awkward-aspect-ratio overflow, failed artwork, redirects, real evidence linkage and rejection of changed source. `npm run test:visual-capture` uses local Chromium and does not contact an AI provider.

This is not the completed Part 8 stage. Policy-bound visual reference comparisons are now implemented and benchmarked; interactive fidelity and full prototype-run validation remain separate checks. A separate candidate-data preview and bounded RTL/long-heading stress are now implemented; their new verification is described below. Captures record redirects; an empty-cart redirect must not be mistaken for an observed populated checkout. Deterministic checks cannot certify aesthetic quality or release eligibility.

The independent provider runner is connected to the review-record/evidence module. Each route gets a fresh vision context, bounded reads of the full captured HTML/layout artifacts and access to its assigned reference evidence and design-pack resources. It has no editing or shell tools. Deterministic detector verdicts are omitted from the capture inventory to avoid steering the assessment. Exact task instructions, hashes, selected skill versions and provider/model are saved as private artifacts. It supplies hash-checked paired screenshots/HTML/layout excerpts, rejects foreign evidence and candidate mismatches, requires explicit accounting for unreviewed captures, and binds each finding to a retrieved capture. Its output never grants release eligibility. Missing submissions, uncertain usage and budget overruns stop the review.

The real prototype produced 42 initial captures with no detected overflow or visibly broken images, but checkout redirected to the empty cart. That coverage gap led to explicit redirect findings and a trusted route-preparation hook. A second run prepared a real cart and captured cart/checkout in all six viewports: 12 captures, correct resolved routes and no deterministic findings. These 54 views are evidence, not an independent aesthetic pass. The original reports remain separate in private runtime storage.

The first real capture run targets the published Satr prototype. Its private report and artifacts live in `.runtime/controller/part-8-pilot/`; no authenticated preview URL or client session state belongs in this repository.

The durable owned API and CLI are implemented. Review records pin the completed builder run, source digest, candidate revision, provider/model and input hash. Queue leases, cancellation, runtime/token budgets, stale-worker fencing, recovery and hash-checked artifact downloads are covered by PostgreSQL integration tests. Active reviews block concurrent agent jobs in the same environment. A `reviewed` status means the assessment finished; inspect `requiresRepair` and `coverageComplete` in its report. It does not mean the website passed QA.

Create a review through `POST /v1/visual-reviews` with a JSON body such as:

```json
{"candidateRunId":"<completed-builder-run-uuid>","maxRuntimeMs":1800000,"maxObservedTokens":1000000}
```

Use `GET /v1/visual-reviews/:id`, `POST /v1/visual-reviews/:id/cancel` and `GET /v1/visual-reviews/:id/artifacts/:artifactId` with the usual controller authentication. CLI equivalents are `visual:create --file review.json`, `visual --id <uuid>` and `visual:cancel --id <uuid>`. These operations become available after compiling and restarting the controller; registering the service alone does not invoke a model.

The processor now allocates a private QA environment from the candidate’s pinned theme bundle, clones its logical database and uploads, and mounts the copied child source/uploads read-only. Cart preparation uses an available simple product in the clone. Variable-only/unavailable-product fixtures may remain unobserved and must report incomplete coverage. The API blocks overlapping agent writes and lifecycle actions on both source and QA environments. Reports use `candidateDataIsolation: isolated-logical-clone` and retain `referenceFidelityVerified: false` and `releaseEligible: false`. Database writes required for cart sessions occur only in the clone. The clone is destroyed after evidence capture, before provider assessment; later review uses immutable artifacts.

Local checks: `npm run test:visual-review` tests evidence and controlled provider behavior; `npm run test:visual-jobs` tests the durable queue/API. `npm run test:visual-agent` is a separate, explicit real-provider benchmark with a 60,000 observed-token cap and four-minute outer deadline. It must catch an introduced short-landscape clipping/overflow defect and cite that capture without attributing the defect to the healthy desktop state. It is not part of the ordinary offline check.

Real-provider benchmark evidence (2026-11-03): run `50f9911b-6413-435a-8977-f08bf813e437` passed in about 72 seconds, using 26,073 confirmed observed tokens. The independent reviewer reported one major landscape defect: the 1600px article overflowed the 844×390 viewport and put its action off screen. It cited the paired screenshot/HTML/layout and did not attribute this defect to the healthy desktop capture. Private artifacts are retained under `.runtime/controller/visual-agent-tests/`. This is one controlled defect-detection proof, not full website QA or a calibrated aesthetic-quality benchmark.

Breakpoint sweep: the trusted processor additionally resizes each critical route around 480, 768 and 1024px (one pixel below, at and above each boundary), at 900px height. Measurements are recorded for every sample; failing states save paired screenshot/HTML/layout evidence. A separate Chromium fixture passes by detecting a 767–769px-only overflow that the six standard profiles miss, and rejecting a changed source digest. Run `npm run test:visual-breakpoints`. This bounded sweep covers CSS/common breakpoint failures, not arbitrary animation settling or every possible width. More than twelve critical routes currently holds the review rather than silently reducing coverage.

Local runtime checkpoint (2026-11-03): the compiled controller and worker were restarted after verifying no active build, agent, intake or environment-operation jobs. The authenticated health endpoint returned 200 and the new review endpoint rejected an empty request with 400. This confirms service registration/input validation without launching a paid review of the retained client prototype.

Candidate isolation implementation: the trusted clone action accepts only a fresh, stopped target in the same project with the same theme bundle. It verifies the source digest, takes a single-transaction dump of InnoDB tables, rewrites URLs with serialization support, resets the target admin credential/copied WordPress sessions, and validates child/media hashes before and after copying. Private dump files are removed before the preview opens. A source/media mismatch, unsupported table engine, capacity limit or failed operation holds the review. Database/media hashes and the allocated environment are recorded. This captures a consistent transactional database plus stable source/media files, not an atomic snapshot spanning all three stores.

Preview allocation is pinned to the review/attempt. Cancellation/failure destroys the target; expiry and interrupted-worker recovery provide durable cleanup fallbacks. The source preview stays in its original environment. A controlled orchestration test verifies allocation-before-copy, cancellation before cloning, failure cleanup and repeated cleanup. The native two-WordPress test passed on 2026-11-03 (about 679 seconds). It verified real copied data, serialization-safe URL replacement, independent database mutations, distinct admin credentials, read-only child/media, a served cloned storefront, source-digest rejection and refusal to overwrite an already initialized target. Both disposable environments were destroyed. Neither isolation test calls an AI provider.

RTL/content stress uses `synthetic-rtl-long-headings-v1`: main headings get long Persian content and RTL direction in the browser DOM, at 390×844 and 844×390. Each captured state is explicitly labelled synthetic and goes to the independent reviewer alongside actual candidate captures. No substitutions are saved to WordPress. Missing eligible headings produce incomplete stress coverage. The local browser fixture passed by finding deliberate nowrap overflow while the original served HTML remained unchanged. Run `npm run test:visual-stress`; broader forms, navigation labels, translations, font failures and dynamic data scenarios remain separate coverage.

The local controller/worker were compiled and restarted again after the isolation/stress regressions passed, applying the QA-preview migration. The authenticated health endpoint returned 200 and an empty review request returned 400. No complete retained-prototype review was queued in this verification slice; no additional AI-provider calls were made.

Visual fidelity now resolves the existing per-page strict-copy/semi-copy/inspiration/custom policy before review. Desktop/mobile candidate captures get comparison slots for non-free layout, typography, palette and imagery axes. `match` requires observed similarity; `adapt` permits departures that follow the client brief and DESIGN.md; `free` does not require a copy comparison. Per-page URL assignments take precedence. With one reference URL, the home page uses that URL and other paths are inferred on its origin; this inference is recorded. Multiple unassigned references, duplicate states, missing responsive captures and unsuccessful reference states cannot silently count as comparisons.

`factory_fidelity_reference` supplies only the assigned immutable paired reference screenshot/HTML/layout states. Submissions must account for each required candidate/axis slot. Satisfied/defect claims require both retrieved candidate and assigned reference evidence. Defects require an evidence-linked reference-fidelity finding; missing or uninspected references must be `unverified`, which keeps overall coverage incomplete. Failed evidence batches grant no viewed credit. Reference comparison completion describes review coverage, not whether the site matched: inspect `requiresRepair` and each verdict. Interactions remain unverified and every result retains `releaseEligible: false`.

Local fidelity tests cover policy overrides, free axes, missing/ambiguous evidence, unseen/foreign references, partial failed batches and unsupported claims. Run `npm run test:visual-fidelity`. The explicit `npm run test:visual-fidelity-agent` benchmark passed on 2026-11-03: the same orange-versus-blue screenshots were defects in both desktop/mobile strict-copy palette comparisons, then satisfied the client's requested semi-copy orange adaptation. Strict copy used 69,462 confirmed observed tokens; semi-copy used 49,563. The semi-copy review required no repair. Private evidence is under `.runtime/controller/visual-fidelity-agent-tests/bc955a6d-f9fd-4d87-bd18-ea133711da7d/`.

The full prototype pilot uses `npm run pilot:visual -- --create --candidate <builder-run-uuid>` once, then `npm run pilot:visual` to resume watching the saved job. It preserves its review ID instead of starting another inference job on restart. Its private state/results live under `.runtime/controller/part-8-pilot/`; it logs only status, route counts and usage summaries. The pilot caps observed tokens at 800,000 and total runtime at one hour. The retained prototype's first run finished capture but held at its first vision route (`visual_review_incomplete`, 240,536 confirmed observed tokens). No pass is claimed. The failure and recovery are documented in [the Part 8 report](PART-8-REPORT.md).

Capture identity correction: inventories now expose an explicit `captureId`, and per-route tool schemas enumerate only valid capture IDs. Screenshot/HTML IDs remain artifact identifiers and cannot be used as review capture references. This fixes the ambiguity observed in the first full pilot. Visual reviewers now receive verified optional pack indexes and controlled access to relevant source sections; core factory rules, client direction and DESIGN.md remain inline. Pack versions/hashes remain recorded, and unread optional material is not claimed as applied. Designer/builder loading remains full.

`npm run pilot:visual:replay -- --review <terminal-review-uuid> --path / --budget 150000` is an operator recovery tool. It checks owned terminal review artifacts and candidate/skill hashes, then evaluates a captured route with the corrected interface. New task/results are stored separately under private pilot replay storage. It does not alter the original durable review status or claim a fresh live preview. It is not the completed durable resumption workflow.

Recovery checkpoint (2026-11-04): the corrected home-route replay stopped on provider HTTP 429. Its instructions shrank from 105,035 to 33,133 characters; recorded usage was 112,507 observed tokens with confirmation false. The original durable review remains needs_review. The initial replay error used the broad budget-error label; its private proxy diagnostic identifies provider_http_failed/429. Future events preserve provider error codes and distinguish visual_review_usage_unconfirmed from actual budget overruns. Further real-provider calls are held.

Durable capture reuse is now supported by POST /v1/visual-reviews (and visual:create) with reuseCaptureReviewId alongside candidateRunId. The source must be an owned terminal review for the exact same candidate revision/source digest and storage root, with all capture reports and clone provenance present. The worker hash-checks the original artifacts and imports paired evidence into its own attempt with new IDs; it preserves the original review. The reused reports identify captureSourceReviewId and freshPreviewObserved:false. They assess the original data snapshot, including its original deterministic defects and coverage gaps. They do not assert that a currently edited site was observed. No new environment or browser is allocated for reuse. Input hashes, ownership, queue leases, budgets and independent review validation still apply.

Offline verification imported the retained pilot's 42 ordinary captures, 12 synthetic captures and 54 breakpoint samples (167 evidence/provenance records) without inference. Tests cover source ownership, terminal status, candidate mismatch, link remapping and damaged artifacts. Queue tests reject missing/foreign snapshot sources. This verifies reuse and artifact integrity; the full provider assessment remains incomplete after the earlier HTTP 429.
